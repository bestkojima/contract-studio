# 功能节点与深 Module

## 属性围绕可观察功能

节点表达功能或具有独立输入输出的处理步骤。一个节点可以由多个函数实现；内部辅助函数在实现详情里定位，无需逐个变成节点。

- **身份与结构**：稳定 ID、标题、类型、父节点。父子表示包含，连线表示数据流或业务依赖；连线不自动调度函数。
- **职责与规则**：描述完成什么、必须遵循的处理规则与顺序。
- **输入输出**：字段、类型、约束、单位与必要示例；复杂输入用 `inputSchema` / `outputSchema`。
- **异常与验收**：触发条件、用户可见错误、可观察的预期行为。需求级验收写在需求源中，节点关联读取，避免复制。
- **运行入口**：`capabilityId` 选择已登记能力；内部函数输入与试运行适配器输入分别描述。

`importance` 按职责区分，独立于节点类型和执行结果：

| 值 | 含义 | 画布颜色 |
| --- | --- | --- |
| `core` | 核心逻辑：决定主要行为和结果 | 紫色 |
| `key` | 关键逻辑：关键校验、依赖与分支 | 琥珀色 |
| `normal` | 普通组成逻辑：组装与辅助职责，默认值 | 蓝灰色 |

颜色与文字并用。位置、折叠、聚焦与重点视图属于展示状态；调整重要性或布局不改变需求确认和业务行为证据。

## 函数划分减少调用方负担

先确定 Module 的输入、输出、错误与状态规则，再划分内部函数。输入适配、业务校验、领域处理、流程组织与界面呈现各自拥有真实职责；后端提供实际业务结果，前端负责交互与反馈。

判断是否存在浅 Module：调用方是否重复理解来源选择、处理顺序和中间状态？把重复知识收回到拥有该规则的 Module。删除一层后调用方更简单的转发层可以直接去掉；内部小函数可以保留，不以文件数量或行数判断深度。

维护追踪读取时使用现有 `openTraceability(root)`：它统一拥有源同步、规则规范化、索引状态与关联投影，调用方查询功能、能力与源码。沿公共 Interface 验证改变的行为，并保持已有入口和使用条件。

## 状态与文档

需求确认覆盖实际确认的内容。现有确认记录只覆盖标题和描述，新增验收条件不能自动继承确认。源码变动与行为变更使相关证据待复验；数据流、声明调用和运行观察分别标明来源。

节点上下文接口同时生成结构化 `context`、说明 `markdown` 与开发任务 `taskMarkdown`。侧栏与 Agent 共用此接口；导出文档是快照，接手时读取当前源。前后端对应按用户能力检查：输入能提交、成功能看到结果、失败有反馈、过程来自真实运行；内部辅助函数只需能定位。
